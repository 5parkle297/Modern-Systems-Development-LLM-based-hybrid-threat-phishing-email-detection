# 第四章 测试方案与实验设计

## 4.1 测试数据集构建

### 4.1.1 数据集选择与来源

为全面评估系统对传统钓鱼、LLM 生成钓鱼以及混合攻击链的检测能力，本实践从多个权威数据源获取测试样本，构建多样化的评估数据集。

**（1）公开学术数据集**

- **Enron Email Dataset**
  来源：卡内基梅隆大学（Carnegie Mellon University）
  网址：https://www.cs.cmu.edu/~enron/
  Zenodo 镜像：https://zenodo.org/records/8339691
  描述：该数据集包含约 50 万封 Enron 公司员工的真实邮件，涵盖正常商务通信、内部协作等场景，可作为正常邮件（Benign）的基准数据。本实践从中随机抽取 100 封邮件作为对照组，用于测试误报率（False Positive Rate, FPR）。

- **APWG eCrime Exchange (eCX) Phishing Database**
  来源：反钓鱼工作组（Anti-Phishing Working Group）
  网址：https://apwg.org/
  描述：APWG 维护的真实钓鱼邮件数据库，包含品牌仿冒、凭证窃取等多种类型的钓鱼样本。由于该数据库需要申请访问权限，本实践通过学术合作渠道获取约 80 封经过脱敏处理的钓鱼邮件样本。

- **SpamAssassin Public Corpus**
  来源：Apache SpamAssassin 项目
  网址：https://spamassassin.apache.org/old/publiccorpus/
  描述：包含垃圾邮件与正常邮件的公开语料库，其中部分垃圾邮件具有钓鱼特征（如虚假中奖、账户验证等）。本实践从中筛选 50 封具有钓鱼诱导性的邮件作为传统钓鱼样本。

- **Datacon 2023 邮件安全赛道数据集**
  来源：Datacon 数据安全竞赛
  GitHub 镜像：https://github.com/yaoyue123/datacon2023-spoof-email
  描述：该数据集专注于邮件欺骗（Email Spoofing）检测，包含发件人伪造、域名欺骗等高级钓鱼技术。本实践选取 60 封带有域名欺骗特征的邮件样本，测试规则引擎与 LLM 对此类攻击的识别能力。

**（2）LLM 生成钓鱼数据集**

- **Kaggle: Human vs LLM Generated Phishing & Legitimate Emails**
  来源：Kaggle 用户 francescogreco97
  网址：https://www.kaggle.com/datasets/francescogreco97/human-llm-generated-phishing-legitimate-emails
  描述：该数据集通过 GPT-3.5 和 GPT-4 生成的钓鱼邮件与正常邮件，模拟攻击者利用 LLM 自动化生成钓鱼内容的场景。本实践选取 70 封 LLM 生成钓鱼样本，测试系统对高度仿真、语法流畅的钓鱼文本的检测效果。

**（3）混合攻击链样本构造**

为模拟"邮件文本 + 仿冒网页"的混合攻击链，本实践采用以下方式构造样本：

- **PhishTank 验证的钓鱼 URL**
  来源：PhishTank（https://www.phishtank.com/）
  方法：从 PhishTank 获取已验证的钓鱼 URL（如仿冒 PayPal、Apple ID 登录页），嵌入到构造的钓鱼邮件中，形成文本 + URL 的复合样本。本实践构造 40 个此类混合样本。

- **自行构造的仿冒登录页**
  方法：使用 HTML/CSS 仿制知名品牌（如 Google、Microsoft、Amazon）的登录页面，部署至测试服务器，嵌入邮件文本中。结合多模态检测模块（VLM 分析截图）测试端到端检测能力。构造样本数：30 个。

### 4.1.2 数据集统计与分布

经过数据收集与筛选，最终构建的测试数据集统计如下：

| 类别                     | 样本数量 | 数据来源                                      |
|--------------------------|----------|-----------------------------------------------|
| **正常邮件（Benign）**   | 100      | Enron Dataset (80) + SpamAssassin (20)        |
| **传统钓鱼邮件**         | 130      | APWG (80) + SpamAssassin (50)                 |
| **LLM 生成钓鱼邮件**     | 70       | Kaggle LLM Phishing Dataset                   |
| **域名欺骗钓鱼邮件**     | 60       | Datacon 2023 Spoof Email Dataset              |
| **混合攻击链（URL+网页）**| 70       | 构造样本（PhishTank URL 40 + 自制仿冒页 30）   |
| **总计**                 | **430**  | -                                             |

数据集分布设计遵循以下原则：

- **正常邮件占比 23%**：模拟真实场景中绝大多数邮件为正常邮件的情况，用于评估误报率。
- **传统钓鱼占比 30%**：涵盖经典钓鱼手法（品牌仿冒、紧急诱导、中奖欺诈等），测试规则引擎与传统特征提取的效果。
- **LLM 生成钓鱼占比 16%**：测试系统对新型 AI 生成钓鱼内容的识别能力。
- **混合攻击链占比 16%**：评估多模态检测模块的贡献。

### 4.1.3 数据预处理与标注

**（1）数据清洗**

- **去除重复样本**：通过邮件 Message-ID 去重，避免重复样本影响评估。
- **敏感信息脱敏**：对包含真实个人信息的邮件进行脱敏处理（如替换真实姓名、邮箱地址），遵守隐私保护原则。
- **格式规范化**：统一转换为 `.eml` 格式，确保邮件解析器可正确处理。

**（2）人工标注**

为确保标签准确性，本实践组织网络安全领域专家对所有样本进行人工标注：

- **标注团队**：3 名具有 5 年以上安全从业经验的专家。
- **标注流程**：每封邮件由至少 2 名专家独立标注，标注结果不一致时通过讨论达成共识。
- **标注标准**：
  - **Phishing（钓鱼）**：明确的凭证窃取意图、恶意 URL、品牌仿冒、附件投毒等。
  - **Suspicious（可疑）**：存在部分钓鱼特征但不完全确定（如可疑措辞但无明显恶意 URL）。
  - **Benign（正常）**：正常商务通信、个人邮件、订阅邮件等。

**（3）数据集划分**

- **测试集**：全部 430 个样本用于测试，不涉及训练（本系统基于规则与预训练 LLM，无需训练）。
- **知识库构建集**：单独收集 200 个已知钓鱼模板（来源于 PhishTank、OpenPhish 等），用于构建 RAG 知识库。

## 4.2 评估指标体系

### 4.2.1 分类性能指标

**（1）混淆矩阵（Confusion Matrix）**

混淆矩阵是分类任务评估的基础工具，本系统采用三分类设定（Phishing、Suspicious、Benign），混淆矩阵定义如下：

|                  | 预测: Phishing | 预测: Suspicious | 预测: Benign |
|------------------|----------------|------------------|--------------|
| **真实: Phishing**   | TP             | FP₁              | FN           |
| **真实: Suspicious** | FP₂            | TS               | FP₃          |
| **真实: Benign**     | FP₄            | FP₅              | TN           |

为简化分析，本实践采用二分类合并策略：将 Phishing 和 Suspicious 合并为 "恶意"（Malicious），Benign 为 "正常"（Benign），简化混淆矩阵如下：

|                  | 预测: 恶意 | 预测: 正常 |
|------------------|-----------|-----------|
| **真实: 恶意**   | TP        | FN        |
| **真实: 正常**   | FP        | TN        |

**（2）核心评估指标**

基于混淆矩阵计算以下指标：

- **准确率（Accuracy）**
  $$\text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN}$$
  反映系统整体判断正确的比例，适用于数据集平衡的场景。

- **精确率（Precision）**
  $$\text{Precision} = \frac{TP}{TP + FP}$$
  反映系统预测为恶意的邮件中，真正为恶意的比例。高精确率意味着低误报率，对用户体验至关重要。

- **召回率（Recall / True Positive Rate）**
  $$\text{Recall} = \frac{TP}{TP + FN}$$
  反映系统成功识别出的恶意邮件占全部恶意邮件的比例。高召回率意味着低漏报率，对安全防护至关重要。

- **F1 值（F1-Score）**
  $$F1 = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$
  综合考虑精确率与召回率的调和平均，适用于平衡两者的场景。

- **误报率（False Positive Rate）**
  $$\text{FPR} = \frac{FP}{FP + TN}$$
  反映系统将正常邮件误判为恶意的比例，直接影响用户信任度。

- **漏报率（False Negative Rate）**
  $$\text{FNR} = \frac{FN}{TP + FN} = 1 - \text{Recall}$$
  反映系统未能识别出的恶意邮件比例，直接关系到安全风险。

### 4.2.2 模块贡献度分析

为量化各检测模块（规则引擎、LLM、RAG、多模态）的贡献，设计以下消融实验（Ablation Study）：

- **完整系统（Full Model）**：所有模块启用。
- **去除 LLM（w/o LLM）**：仅保留规则引擎 + RAG + 多模态。
- **去除 RAG（w/o RAG）**：仅保留规则引擎 + LLM + 多模态。
- **去除多模态（w/o Multimodal）**：仅保留规则引擎 + LLM + RAG。
- **仅规则引擎（Rule-only）**：仅保留规则引擎。
- **仅 LLM（LLM-only）**：仅保留 LLM 检测。

通过对比各配置下的 F1 值，量化每个模块的边际贡献。

### 4.2.3 性能与成本指标

**（1）推理时间（Inference Time）**

记录每封邮件从上传到返回结果的总耗时，细分为：
- 邮件解析时间
- 特征提取时间
- 规则引擎检测时间
- LLM API 调用时间
- RAG 检索时间

**（2）批量自动化测试**

目标：对全部 430 个测试样本执行检测，收集性能指标。

脚本示例（Python）：

```python
import requests
import json
import time
import os
from pathlib import Path

API_BASE_URL = "http://localhost:8000/api/v1"
TEST_DATA_DIR = Path("./test_data/")

def test_email_batch():
    results = []

    for eml_file in TEST_DATA_DIR.glob("**/*.eml"):
        # 读取标签（从文件名或元数据）
        true_label = extract_label_from_filename(eml_file)

        # 上传邮件
        with open(eml_file, 'rb') as f:
            files = {'file': f}
            upload_resp = requests.post(f"{API_BASE_URL}/upload/", files=files)
            job_id = upload_resp.json()['job_id']

        # 执行检测
        start_time = time.time()
        detect_resp = requests.post(f"{API_BASE_URL}/detect/{job_id}")
        end_time = time.time()

        result = detect_resp.json()
        result['true_label'] = true_label
        result['processing_time'] = end_time - start_time
        result['filename'] = eml_file.name

        results.append(result)
        print(f"Processed: {eml_file.name} | Predicted: {result['label']} | True: {true_label}")

    # 保存结果
    with open('test_results.json', 'w') as f:
        json.dump(results, f, indent=2)

    return results

def extract_label_from_filename(filepath):
    """从文件名提取标签（假设格式为 phishing_001.eml）"""
    filename = filepath.stem.lower()
    if 'phishing' in filename or 'malicious' in filename:
        return 'phishing'
    elif 'benign' in filename or 'normal' in filename:
        return 'benign'
    else:
        return 'suspicious'

if __name__ == "__main__":
    results = test_email_batch()
    print(f"Total samples tested: {len(results)}")
```

**（2）指标计算脚本**

```python
import json
import numpy as np
from sklearn.metrics import confusion_matrix, classification_report, accuracy_score

def calculate_metrics(results_file):
    with open(results_file, 'r') as f:
        results = json.load(f)

    # 提取真实标签与预测标签
    y_true = [r['true_label'] for r in results]
    y_pred = [r['predicted_label'] for r in results]

    # 二分类转换（合并phishing和suspicious为malicious）
    y_true_binary = ['malicious' if label in ['phishing', 'suspicious'] else 'benign' for label in y_true]
    y_pred_binary = ['malicious' if label in ['phishing', 'suspicious'] else 'benign' for label in y_pred]

    # 计算指标
    print("=== Binary Classification Metrics ===")
    print(classification_report(y_true_binary, y_pred_binary))

    # 混淆矩阵
    cm = confusion_matrix(y_true_binary, y_pred_binary, labels=['malicious', 'benign'])
    print("\nConfusion Matrix:")
    print(cm)

    # 计算FPR、FNR
    tn, fp, fn, tp = cm.ravel()
    fpr = fp / (fp + tn)
    fnr = fn / (fn + tp)
    print(f"\nFalse Positive Rate: {fpr:.4f}")
    print(f"False Negative Rate: {fnr:.4f}")

    # 统计处理时间
    processing_times = [r['processing_time'] for r in results]
    print(f"\n=== Performance Metrics ===")
    print(f"Average processing time: {np.mean(processing_times):.2f}s")
    print(f"Median processing time: {np.median(processing_times):.2f}s")
    print(f"Max processing time: {np.max(processing_times):.2f}s")

if __name__ == "__main__":
    calculate_metrics('test_results.json')
```

## 4.4 案例分析设计

### 4.4.1 典型案例选择

从测试结果中筛选以下典型案例进行深入分析：

**（1）传统钓鱼邮件检测成功案例**

选择标准：规则引擎命中多条规则，LLM 高置信度判定为钓鱼。

示例：仿冒 PayPal 的账户验证邮件，包含短链接、紧急语气、SPF 认证失败。

**（2）LLM 生成钓鱼邮件检测成功案例**

选择标准：规则引擎命中规则较少（语法流畅、无明显统计异常），但 LLM 成功识别。

示例：GPT-4 生成的银行账户安全提醒邮件，措辞专业但暗含凭证窃取意图。

**（3）混合攻击链检测成功案例**

选择标准：多模态模块成功识别嵌入的仿冒登录页截图。

示例：邮件文本正常，但链接指向仿冒 Google 登录页，VLM 分析截图发现品牌冒用。

**（4）误报案例（False Positive）**

选择标准：正常邮件被误判为钓鱼或可疑。

示例：企业内部发送的密码重置通知，因包含"verify your account"等短语被规则引擎标记，但 LLM 正确判定为正常。

**（5）漏报案例（False Negative）**

选择标准：钓鱼邮件未被成功识别。

示例：高度定制化的商务邮件妥协（Business Email Compromise, BEC）攻击，措辞正常且无恶意 URL，所有模块均未检测到威胁。

### 4.4.2 案例分析维度

针对每个案例，从以下维度进行分析：

- **邮件内容摘要**：Subject、From、核心文本片段、URL 等。
- **各模块检测结果**：规则引擎命中规则、LLM 判别与理由、RAG 匹配模板、多模态发现。
- **融合后的最终结果**：标签、分数、置信度。
- **成功/失败原因分析**：哪些特征起到关键作用？哪些模块贡献最大？为何出现误报/漏报？
- **改进建议**：针对失败案例，提出规则优化、Prompt 改进、知识库扩充等改进方向。

## 4.5 可解释性评估

### 4.5.1 可解释性评估维度

除了分类性能，本实践还评估系统的可解释性，确保检测结果对用户可理解、可信赖。

**（1）规则命中可理解性**

评估标准：用户能否理解规则的含义？

示例：
- 优秀："检测到短链接 bit.ly"（清晰）
- 一般："规则 R17 触发"（需查阅规则定义）

**（2）LLM 推理质量**

评估标准：LLM 输出的 reasoning 是否合理、具体、有说服力？

评分标准（1-5 分）：
- 5 分：详细列举具体证据（如"主题包含'urgent'，发件人域名与 Reply-To 不一致"）
- 3 分：给出笼统理由（如"邮件存在可疑特征"）
- 1 分：无理由或理由错误

**（3）安全建议实用性**

评估标准：建议是否具体、可操作？

示例：
- 优秀："立即修改您的 PayPal 密码，并通过官网 paypal.com 登录检查账户状态"
- 一般："建议谨慎处理"

### 4.5.2 用户满意度调查（可选）

邀请 10 名非技术背景用户体验系统，通过问卷收集反馈：

1. 检测结果是否易于理解？（1-5 分）
2. LLM 给出的理由是否有说服力？（1-5 分）
3. 安全建议是否实用？（1-5 分）
4. 整体界面体验如何？（1-5 分）

## 4.6 本章小结

本章详细设计了混合威胁钓鱼邮件检测系统的测试方案与实验流程。首先，通过整合 Enron、APWG、SpamAssassin、Datacon 2023、Kaggle LLM Phishing 等多源数据集，构建包含 430 个样本的多样化测试集，覆盖正常邮件、传统钓鱼、LLM 生成钓鱼、域名欺骗及混合攻击链等场景。其次，建立了全面的评估指标体系，包括分类性能指标（准确率、精确率、召回率、F1 值、误报率、漏报率）、模块贡献度分析（消融实验）以及性能与成本指标（推理时间、API 调用成本、吞吐量）。实验设计包含基础功能测试、批量自动化测试、消融实验三个层次，并通过脚本自动化执行与数据收集。此外，设计了典型案例分析与可解释性评估方案，确保系统不仅性能优异，还具备良好的用户体验与可信度。本章为后续第五章的结果分析与讨论奠定了坚实的方法论基础。
